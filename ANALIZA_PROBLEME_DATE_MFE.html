  • Fără diacritice: s, t, a, i, a

🔴 Problema #5: Formate Diferite pentru Date Numerice

❌ Virgulă vs Punct - Același Tip de Date, Formate Diferite

Datele de progres vin în 2 formate complet diferite din API:

// Din RawAPIData interface (PNRRDataAggregation.ts, liniile 218-219) progres_fizic?: string; // ← STRING cu virgulă: "0,16" progres_financiar?: number | null; // ← NUMBER cu punct: 0.029999999999999999 // Exemplu date reale din API: { "progres_fizic": "0,16", // STRING cu virgulă "progres_financiar": 0.03 // NUMBER cu punct } // SAU când datele lipsesc (ambele null - CORECT): { "progres_fizic": null, // NULL - OK ✓ "progres_financiar": null // NULL - OK ✓ }
⚠️ Clarificare:

Problema NU este null (care este o valoare validă în JSON pentru "lipsă date"). Problema este inconsistența de format când datele EXISTĂ: de ce progres_fizic este STRING cu virgulă, iar progres_financiar este NUMBER cu punct? Ambele ar trebui să fie NUMBER cu punct pentru consistență!

Câmp Tip Date Format Exemplu
progres_fizic STRING Virgulă (format românesc) "0,16", "0,85"
progres_financiar NUMBER Punct (format JSON standard) 0.029999999999999999, 0.85

De ce această diferență?

  • progres_fizic (STRING cu virgulă): MFE folosește probabil Excel/CSV românesc care exportă cu virgulă ca separator zecimal
  • progres_financiar (NUMBER cu punct): Exportat corect ca JSON numeric standard
  • Inconsistență: Același tip de date (progres) ar trebui să aibă același format!
// Cod necesar pentru conversie (MapView.jsx, linia 360, 616, 3494) const progresFizicStr = String(progresFizic).replace(',', '.') percentage = Math.round(parseFloat(progresFizicStr) * 100) // progres_financiar nu necesită conversie - deja numeric const percentage = Math.round(progresFinanciar * 100)

❌ Floating Point Precision

Problema clasică JavaScript/JSON cu precizia numerelor zecimale:

  • 0.029999999999999999 în loc de 0.03
  • 0.5554582 - precizie excesivă (7 zecimale)
  • Necesită rotunjire manuală în aplicație
// Exemplu din date reale API { "progres_fizic": "0,16", // ← STRING, virgulă "progres_financiar": 0.029999999999999999 // ← NUMBER, punct, precizie excesivă }

🟡 Problema #8: Risc Valori Fără Zero în Față (Potențial)

⚠️ Format Numeric Incomplet - Risc de Parsing

Deși nu a fost detectată în datele actuale, există riscul ca valori zecimale să fie exportate fără zero în față:

// Risc potențial (NU detectat în date actuale): { "progres_fizic": ",35" // ✗ GREȘIT - fără zero în față "progres_fizic": ",549834" // ✗ GREȘIT - fără zero în față } // Format corect (prezent în date actuale): { "progres_fizic": "0,35" // ✓ CORECT - cu zero în față "progres_fizic": "0,549834" // ✓ CORECT - cu zero în față }

De ce e risc?

  • Excel/CSV export: Unele sisteme pot exporta 0.35 ca ",35" (fără zero)
  • Parsing JavaScript: parseFloat(",35") returnează NaN (Not a Number)!
  • Validare JSON: ",35" este string valid în JSON, dar nu poate fi convertit la număr
  • Calcule eșuate: Toate calculele cu NaN returnează NaN
// Exemplu problemă: const progres = ",35"; const parsed = parseFloat(progres.replace(',', '.')); // parseFloat(".35") = 0.35 ✓ Funcționează! // DAR dacă uiți replace: const parsed2 = parseFloat(progres); // parseFloat(",35") = NaN ✗ Eșuează! // Soluție robustă în cod (MapView.jsx, linia 365): let str = String(progresFizic).trim(); if (str.startsWith(',')) str = '0' + str; // Fix pentru ",35" → "0,35" const parsed = parseFloat(str.replace(',', '.'));
